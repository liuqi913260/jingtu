# 竞途 V1.0 MVP 开发计划

> 基于：PRD.md
>
> 目标：按本计划执行后，得到一个可离线运行、可演示、可验收的大学生竞赛总览与组队协作网页 App。
>
> 计划版本：V1.0
>
> 更新日期：2026-10-27

## 1. 执行说明

### 1.1 开发目标

第一版以浏览器本地运行作为交付目标，先完成 PRD 中的 P0 功能，再完成 P1 中的收藏、今日计划和本地备份恢复。第一版不接真实后端，不实现真实私信和云同步。

交付结果必须满足：

- 直接打开 index.html 或通过静态服务器即可运行。
- 无网络时仍能完成核心演示。
- 刷新页面后，用户、比赛、招募、收藏和计划数据不丢失。
- 通过导出/导入 JSON 可以迁移本地数据。
- 通过 PRD 第 10 节的验收清单。

### 1.2 建议执行节奏

以 1 名开发者为基准，预计 8–10 个工作日；如果多人并行，仍必须按本文定义的数据契约和任务依赖执行。

| 阶段 | 内容 | 建议用时 | 产出 |
| --- | --- | ---: | --- |
| Phase 0 | 现状盘点、环境和任务基线 | 0.5 天 | 基线记录、任务分支 |
| Phase 1 | 数据模型和存储层 | 1 天 | storage.js、数据契约、迁移逻辑 |
| Phase 2 | 应用外壳和共享交互 | 1 天 | 导航、路由、Toast、Modal、空状态 |
| Phase 3 | 认证和个人资料 | 1 天 | 登录/注册、用户状态、资料编辑 |
| Phase 4 | 赛事广场和发布比赛 | 1.5 天 | 列表、筛选、搜索、详情、发布 |
| Phase 5 | 找队友和发布招募 | 1 天 | 招募列表、筛选、联系、发布 |
| Phase 6 | 知识库和今日计划 | 1.5 天 | 知识详情、计划添加/完成 |
| Phase 7 | 收藏、我的发布、备份恢复 | 1.5 天 | P1 数据能力和恢复工具 |
| Phase 8 | 测试、修复和交付 | 1–2 天 | 验收记录、发布包 |

### 1.3 开发原则

- 先确定数据契约，再写页面模板。
- 页面只负责展示和触发事件，读写数据统一经过存储层。
- 任何新功能都必须同时定义：数据字段、空状态、错误状态、成功反馈和刷新后的持久化行为。
- 先完成可运行的最小流程，再做视觉细节。
- 不在第一版引入需要后端才能验证的功能。
- 每个阶段完成后立即按该阶段验收，不把问题全部推迟到最后。

## 2. 当前代码基线和需要补齐的内容

当前项目已有三个主要文件：

- index.html：应用外壳、侧边栏、顶部栏、Modal 容器和 Toast 容器。
- styles.css：桌面端和窄屏布局、卡片、表单、弹窗样式。
- app.js：单文件状态、示例赛事、招募、知识内容、视图渲染、登录和发布流程。

当前原型可以作为视觉和交互基线，但在开发计划中需要进行以下结构化改造：

| 当前原型能力 | 需要改造或补齐 | 目标 |
| --- | --- | --- |
| app.js 同时承载数据、页面和事件 | 拆分模块 | 降低后续维护成本，统一数据入口 |
| jt_competitions、jt_teams、jt_user 分散存储 | 统一版本化数据文档 | 支持备份、恢复、迁移 |
| 赛事/招募可发布 | 补齐作者 ID、时间、编辑/删除权限 | 支持“我的发布” |
| 知识卡片为静态摘要 | 增加详情数据和详情入口 | 满足知识库验收 |
| 搜索只覆盖赛事卡片 | 改为跨赛事、招募、知识统一搜索 | 满足 PRD 全局搜索 |
| 通知按钮为占位 | 保持占位并明确不进入 P0 | 控制 MVP 范围 |
| 没有今日计划、收藏 | 新增数据模型和 UI | 完成 P1 |
| 没有导出/导入 | 新增 JSON 备份工具 | 完成数据迁移要求 |

改造时优先保证已有视觉效果不被破坏，再逐步拆分文件。

## 4. 数据契约和存储设计

### 4.1 根数据结构

所有数据统一存放在一个版本化对象中：

    {
      app: 'jingtu',
      schemaVersion: 1,
      data: {
        users: [],
        currentUserId: null,
        competitions: [],
        recruitments: [],
        knowledge: [],
        favorites: [],
        todayPlans: [],
        settings: {}
      }
    }

建议使用一个主 key：jingtu:store。为了兼容当前原型，Phase 1 迁移时读取 jt_user、jt_competitions、jt_teams，成功迁移后写入新结构。

### 4.2 实体字段

#### User

    { id, account, password, name, school, major, preferences: [], createdAt, lastLoginAt }

第一版本地原型可以保留密码用于演示，但导出备份必须删除 password 字段；界面不能宣称该密码具备真实安全能力。

#### Competition

    { id, organizer, name, content, category, region, deadline, deadlineLabel,
      status, isFeatured, hotScore, authorId, createdAt, updatedAt }

其中 organizer 对应 PRD 的学校/主办方；所有日期使用可排序的 ISO 日期或明确的 YYYY-MM-DD。

#### Recruitment

    { id, authorId, authorName, school, title, contestId, description,
      roles: [], currentCount, recruitStatus, createdAt, updatedAt }

#### Knowledge

    { id, title, summary, body, category, tags: [], readMinutes, createdAt, updatedAt }

#### Favorite

    { id, userId, targetType: 'competition' | 'knowledge', targetId, createdAt }

#### TodayPlan

    { id, userId: null, sourceType: 'competition' | 'knowledge' | 'recruitment',
      sourceId, title, planDate: 'YYYY-MM-DD', completed, createdAt, completedAt }

### 4.3 存储 API

storage.js 至少提供：

- loadStore()
- saveStore(store)
- resetStore()
- getStoreVersion()
- migrateStore(input)
- exportStore()
- validateBackup(input)
- importStore(input, mode = 'replace')

业务模块不得直接调用 localStorage.setItem。所有写操作完成后必须触发统一的 store:changed 事件或等价刷新机制。

## 5. 分阶段可执行任务

## Phase 0：基线、环境和任务准备

### 目标

确认现有原型可以运行，建立开发检查入口，避免在重构过程中丢失现有功能。

### 任务

- [ ] P0-01：运行 node --check app.js，记录语法检查结果。
- [ ] P0-02：打开 index.html，确认首页、导航、登录弹窗、比赛发布和招募发布可操作。
- [ ] P0-03：建立 Git 检查点，提交信息建议为 chore: baseline prototype before v1 development。
- [ ] P0-04：建立 tests/acceptance-checklist.md，复制 PRD 第 10 节作为逐项勾选表。
- [ ] P0-05：记录当前浏览器支持范围：最新版 Chrome/Edge，移动端以响应式宽度为主。

### 完成条件

- 当前原型可启动。
- 没有阻断首屏渲染的 JavaScript 错误。
- 基线提交或备份已保留。

## Phase 1：数据层、版本化存储和迁移

### 目标

建立后续所有模块都能复用的统一数据来源。

### 任务

- [ ] P1-01：创建 constants.js，集中定义分类、赛事状态、招募状态、存储 key 和 schema 版本。
- [ ] P1-02：创建默认示例数据：至少 4 条赛事、3 条招募、6 条知识内容。
- [ ] P1-03：创建 storage.js，实现初始化、读取、写入和异常兜底。
- [ ] P1-04：将当前 jt_user、jt_competitions、jt_teams 迁移到 jingtu:store。
- [ ] P1-05：实现字段默认值填充和基础类型校验。
- [ ] P1-06：为所有记录统一补充 id、createdAt、updatedAt。
- [ ] P1-07：将 app.js 中的硬编码业务数组改为从状态层读取。
- [ ] P1-08：模拟 localStorage 不可用或内容损坏，确认应用可以回退到默认数据并提示用户。

### 完成条件

- 刷新页面后默认数据和已发布数据都存在。
- 清空旧 key 后重新打开页面，应用能初始化新 schema。
- 业务代码不再直接写旧 key。
- 主数据结构符合本计划第 4 节。

### 目标

让所有页面使用一致的布局、导航、弹窗、反馈和空状态。

### 任务

- [ ] P2-01：保留 index.html 的应用外壳，补充统一的 main 容器和页面挂载点。
- [ ] P2-02：实现页面路由状态：dashboard、competitions、teams、knowledge、my-posts、profile。
- [ ] P2-03：抽出 renderLayout()、renderPage()、setActiveNav()。
- [ ] P2-04：统一 Modal 打开/关闭、遮罩点击关闭、Esc 关闭和焦点可用性。
- [ ] P2-05：统一 Toast：成功、错误、登录提示、导入失败提示。
- [ ] P2-06：统一空状态组件，至少覆盖无搜索结果、无发布、无今日计划、未登录。
- [ ] P2-07：处理移动端 320–767px 宽度下的导航、表格/卡片和弹窗。
- [ ] P2-08：增加按钮 loading/disabled 约定，避免重复提交。

### 完成条件

- 左侧导航切换所有页面，选中状态一致。
- 页面切换不刷新整个浏览器。
- 所有主要动作都有可见反馈。
- 手机宽度无横向滚动。

## Phase 3：登录、注册和个人资料

### 目标

提供本地演示身份，并让发布、联系和我的页面拥有明确的权限状态。

### 任务

- [ ] P3-01：实现注册表单：账号、密码、昵称、学校。
- [ ] P3-02：实现登录表单：账号、密码；错误账号或密码给出明确提示。
- [ ] P3-03：实现退出登录，并清理当前用户引用，不删除用户数据。
- [ ] P3-04：刷新页面后从 currentUserId 恢复登录状态。
- [ ] P3-05：完善 profile 页面，支持昵称、学校、专业和竞赛方向编辑。
- [ ] P3-06：实现权限守卫：发布比赛、发布招募、联系队长、查看我的发布需要登录。
- [ ] P3-07：统计当前用户发布数量、收藏数量和今日计划数量。

### 完成条件

- 注册 → 登录 → 刷新 → 仍登录 → 退出的链路完整。
- 游客浏览公开内容不被阻止。
- 受保护操作均能引导到登录。
- 资料修改刷新后仍然存在。

### 任务

- [ ] P4-02：实现类别筛选、地区筛选和状态筛选。
- [ ] P4-03：实现按截止日期、热度排序。
- [ ] P4-04：实现比赛详情 Modal 或独立详情视图，展示完整比赛内容。
- [ ] P4-05：实现发布比赛表单：学校/主办方、比赛名字、比赛内容、类别、地区、截止日期、状态。
- [ ] P4-06：校验比赛名称、主办方、内容为必填，截止日期格式正确。
- [ ] P4-07：发布成功后写入作者 ID、创建时间，列表和首页统计立即刷新。
- [ ] P4-08：实现收藏/取消收藏，并只允许当前登录用户修改自己的收藏。

- [ ] P4-10：将全局搜索接入赛事名称、内容、主办方和类别。

- 新发布的比赛可以在赛事广场、首页和我的发布中看到。
- 筛选、排序、搜索结果正确组合，不会只改变视觉而不改变数据。

## Phase 5：找队友和发布组队招募

### 目标

实现学生发布组队需求、筛选招募和联系队长的核心协作闭环。

### 任务

- [ ] P6-06：实现 todayPlans 数据层和去重规则：同一用户、同一来源、同一天不能重复添加。
- [ ] P6-07：在赛事详情提供“加入今日计划：报名准备/关注比赛”。
- [ ] P6-08：在知识详情提供“加入今日计划：今天学习”。

## 6. 关键业务流程的执行顺序

### 6.1 新用户发布比赛

打开首页 → 点击“发布比赛” → 权限守卫发现未登录 → 注册/登录 → 打开发布表单 → 填写并校验必填字段 → 生成 competition 记录 → storage.saveStore() → 刷新赛事列表、首页统计、我的发布 → Toast 显示发布成功。

### 6.2 学生找队友并加入今日计划

找队友 → 按角色筛选 → 打开招募详情 → 点击联系队长 → 登录用户显示联系成功 → 点击加入今日计划 → 生成 todayPlan，按 userId/sourceId/planDate 去重 → 首页今日计划区块出现未完成任务。

### 6.3 备份恢复

个人资料/设置 → 导出数据 → 生成无密码 JSON → 用户清空浏览器数据 → 选择备份文件 → parse JSON → validateBackup() → 用户确认覆盖 → migrateStore() → saveStore() → reloadState() → 首页、列表、个人资料恢复。

## 7. 任务依赖和阻塞处理

### 7.1 依赖关系

Phase 0 → Phase 1 数据层 → Phase 2 应用外壳 → Phase 3 认证 → Phase 4 赛事 → Phase 5 找队友 → Phase 6 知识库和今日计划 → Phase 7 我的发布和备份恢复 → Phase 8 验收交付。

Phase 4 与 Phase 5 在认证完成后可以部分并行；Phase 6 必须使用稳定的赛事、招募和知识数据契约；Phase 7 必须在所有实体字段稳定后开始。

### 7.2 阻塞规则

- 数据字段未确定前，不开始依赖该字段的页面开发。
- 存储迁移未通过前，不删除当前原型旧 key。
- 认证未完成前，可以开发公开列表，但不能实现依赖用户身份的删除、收藏和计划功能。
- 备份恢复必须在所有实体字段稳定后开发，否则会重复修改 schema。
- 任何 P0 失败优先于视觉优化。

## 11. 后续版本入口

V1.0 完成后，再根据真实使用反馈决定是否进入以下方向：

1. 服务端账号、数据库和多端同步。
2. 真实私信、组队申请和通知。
